# 多会话调度设计（v2 草案）

> 状态：**草案，未落地**。当前代码仍是「单会话 + 逐帧 OCR」。
> 目的：把「模拟人类看微信并决定回不回」这件事拆成一个能实现的状态机。
> 读者：后续改 `lib/poller.js` 的人（主要是我自己）。

---

## 0. 一句话

**平时停在聊天列表，靠「未读数变化」发现有群在说话；进群后靠「聊天区 + 有人@我 标签」确认要不要接；一旦接上（开了讨论串）就不再离开这个会话，直到讨论串自然结束。**

---

## 1. 现状与它的问题

### 1.1 现在怎么跑

`lib/poller.js` 的 `capture()` 每 4 秒（probeSec）做一次：

```
dumpsys 前台 → adb 截图 → 哈希/差分 → 整屏 OCR(vl_ocr 4B) → 文本差分
  → 判官(judge_worth 4B) → 决定唤醒 → 唤醒后 agent 用 wechat_send 发出去
```

只盯**一个**会话（`autoReply.whitelistChats[0]`），而且靠「帧变了」驱动。

### 1.2 已经踩到的坑

| 现象 | 根因 |
|---|---|
| 浮层通知被当成聊天消息 | 别的会话的横幅画在聊天区上方，OCR 把它读成 `微信：刚刚` |
| 群里 @ 被后续消息刷掉 | 聊天列表只显示最后一条预览 |
| @ 没被及时识别 | OCR 把 `@升天肥鱼` 读丢（Windows OCR），4B 才读对 |
| DSH 一顿一顿 | `capture()` 全程 `execFileSync`，单帧 3.8 秒阻塞事件循环 |
| 笔记本 6GB 显存 | 4B 模型 + 8192 ctx 溢出到 CPU，会拖死整机 |

---

## 2. 目标 / 非目标

**目标**

1. 能同时"关注"多个会话，但同一时刻只处理一个。
2. @ 我 的消息，即使中间夹了几十条，也不漏。
3. 讨论串进行中，不切窗口、不重读整屏。
4. 空闲时几乎不花算力（不跑 4B）。

**非目标**

- 不做多窗口并行聊天（做不到，也不该做）。
- 不读微信数据库、不逆向协议。
- 不保证"秒回"；宁可慢 10 秒，也不要回错。

---

## 3. 硬约束（不可违背）

1. **单窗口**：手机同一时刻只有一个前台会话。切群 = 切走 = 当前上下文丢失。
2. **一个讨论串**：全局只允许一个活跃讨论串（现有 `poller-threads.json` 的 `t1..tN`）。
3. **读屏是唯一输入**：只能靠 adb 截图 + OCR；没有结构化消息 API。
4. **前台无系统通知**：微信在前台时**不投递系统通知**（实测 `dumpsys notification` 2 分钟零变化）。通知接口只在后台时可用，不能当主信号。
5. **4B 单帧 ~2.1 秒**（笔记本，暖机）；冷启动 6~9 秒。所以"多读几屏"是有成本的。

---

## 4. 可用信号与可信度

| 信号 | 从哪拿 | 存活时间 | 会被覆盖吗 | 成本 | 用途 |
|---|---|---|---|---|---|
| **未读角标** | 列表行 | 直到进会话 | 否，只累加 | 一次列表 OCR | **主触发器** |
| 列表预览文本 | 列表行 | 到下一条消息 | **会** | 同上 | 辅助判断（群里带 `昵称: `） |
| 聊天区消息 | 会话页 | 一直在 | 否（除非滚出屏） | 2.1s/屏 | **判 @ / 内容** |
| 「有人@我」标签 | 群聊顶部 | 直到读了那条 | 否 | 一次点击 + 等滚动 | **兜底跳转** |
| 横幅弹窗 | 非当前页面 | 3~5 秒 | 是 | — | 不可靠，**不用** |
| 系统通知记录 | `dumpsys notification` | 仅后台 | — | 0.1s | 不做主路 |

**结论**：触发靠未读数，判定靠聊天区，跳转靠标签。横幅和通知都不进主链路。

## 5. 状态机

```
                    ┌──────────────────────────────────────────┐
                    │                                          │
                    ▼                                          │
    ┌───────────────────────────┐   未读数↑    ┌───────────────────────────┐
    │  A. IDLE（停在聊天列表）   │ ──────────▶ │  B. ENTERING（进群确认）    │
    │  每 15s 扫一次列表         │             │  读当前屏 → @ 可见?        │
    └───────────────────────────┘             └───────────────────────────┘
                    ▲                                   │        │
                    │ 不值得回/失败                       │ 值得回 │ @ 不可见
                    │                                   ▼        ▼
                    │                        ┌──────────────┐ ┌────────────────┐
                    │                        │ C. THREAD    │ │ 点「有人@我」   │
                    │                        │ （留在此会话）│ │ 等滚动停再读    │
                    │                        └──────────────┘ └────────────────┘
                    │                                   │
                    └──── 沉默 > 10min / 明显收尾 ────────┘
```

### A. IDLE

- 位置：聊天列表页。
- 动作：每 `listScanSec`（默认 15 秒）截一张列表，OCR 每行。
- 产出：`[{name, unread, preview, isGroup}]`。
- 迁移条件：某行 `unread > lastUnread[chat]` → 选它 → 进 B。
- 选择优先级：`@我`（若列表可见） > 私聊 > 群聊活跃度。
- **每轮最多选一个**；选中后其它群的未读继续攒着，不处理。

### B. ENTERING

- 动作：点该行 → 等 300~500ms → 截屏 → OCR。
- 判定 1：**@ 是否在当前屏内**（文本含 `@` + 自己的关键词）。
  - 是 → 直接拿这一屏做判定，跳到"判定"。
  - 否 → 进"标签跳转"分支。
- 判定 2（群 vs 私聊）：见 §6.4。
- 判定 3：值得回吗（@我 / 提问 / 关键词 / 有梗的图）→ 是则转 C，否则回 A。

### 标签跳转（B 的子流程）

```
找「有人@我」标签（OCR 顶部条 / 模板匹配）
  ├ 找不到 → 回退：向上翻屏，最多 3 屏，找上一水位线
  └ 找到 → 点击 → 等滚动停 → 截屏 → OCR → 判定
```

**等滚动停**（关键）：

```
每 400ms 截一帧，算整图哈希
连续 2 帧哈希相同 → 认为停稳
或累计 > 5s → 放弃本次（记冷却，回 A）
等待期间：不写 inbox、不唤醒、探针静默
```

### C. THREAD

- 位置：固定在这个会话，**不再扫列表**。
- 动作：沿用现有 4 秒探帧 + OCR 差分。
- 判定：@ 我 / 续聊线索 / 关键词 → 回；否则只更新水位线。
- 迁移条件：
  - 沉默超过 `threadTtlMin`（默认 10 分钟），或
  - 对方明显收尾（"睡了""拜拜"等，后续可做），或
  - 发送失败/被踢出会话 → 回 A。

## 6. 关键流程细节

### 6.1 列表扫描

- 截图 → OCR → 逐行解析：`名称 / 未读数 / 预览 / 是否群`。
- 群识别：预览形如 `昵称: 内容`（冒号前是已知昵称/短文本且不含句末标点）。
- 保存 `lastUnread[chat]`；只在"变大"时触发，**变小或归零不触发**。
- 一次 OCR 覆盖一屏约 8~10 行；列表超过一屏时先只处理可见行（够用）。

### 6.2 进群确认

- 点击行的坐标由行高推算（现有 `coords` 里有列表相关坐标可复用）。
- 点击后等 `enterSettleMs`（默认 500ms）再截图。
- 判断当前会话名：读标题栏（这次 4B 有机会读对，因为标题在屏内）。

### 6.3 点标签 + 等滚动停

见 §5 子流程。注意：

- 标签只在 **@ 不在可见区** 时出现；
- 滚动是动画，**不能点完立刻截图**；
- 失败（5 秒没停）→ 本次放弃，给该群 90 秒冷却。

### 6.4 群 vs 私聊

三选一，任一条即可：

1. 列表预览有无 `昵称: ` 前缀；
2. 会话标题是否带 `(N)` 成员数；
3. 消息气泡上方有无灰色昵称行。

私聊：没有昵称行、标题是纯名字。
用途：私聊可以直接视为"一定在跟我说话"，群聊才需要 @ / 判官筛。

### 6.5 讨论串

沿用现有 `state.threads`：

- 开串：判定"值得回"且当前无活跃串。
- 续串：收到该会话新消息且串未过期。
- 关串：TTL 到期 / 发送失败 / 显式收尾。
- **串活着时 IDLE 的列表扫描应暂停**（否则会把屏幕切走）。

### 6.6 水位线与翻屏

- 每个会话维护 `watermark = 上次处理到的最后一行文本`。
- 进会话后从最新屏往上找，命中 watermark 即停。
- 翻屏上限 3 屏；超过则只处理最新屏，并把 `missed` 记进日志（不假装看过）。

## 7. 数据结构（草案）

```js
// 每个会话一份，落盘 data/sessions.json
session = {
  key: "毁灭菇翘嘴软饭群",      // 去未读数后的标题
  isGroup: true,
  lastUnread: 15,              // 上次看到的未读数
  watermark: "球球别抓我：小鬼子…", // 上次处理到的最后一行
  cooldownUntil: 0,            // 进群/跳转失败的冷却
  lastEnterAt: 0,
}

// 运行态（内存）
state.mode = "idle" | "entering" | "thread";
state.current = null;          // 当前绑定的 session key（单窗口锁）
state.scrollSettling = false;  // 等滚动期间：探针静默
```

## 8. 参数

| 参数 | 默认 | 理由 |
|---|---|---|
| `probeSec` | 4 | 线程内的探帧节奏（沿用） |
| `listScanSec` | 15 | 无未读丢失风险，够快 |
| `enterSettleMs` | 500 | 进会话的页面切换 |
| `scrollSampleMs` | 400 | 滚动停采样间隔 |
| `scrollStableFrames` | 2 | 连续两帧一致判停 |
| `scrollTimeoutMs` | 5000 | 超时放弃 |
| `threadTtlMin` | 10 | 沿用现有 |
| `perChatCooldownSec` | 90 | 防止被活跃群牵着 |
| `maxScrollScreens` | 3 | 无标签时的兜底上限 |
| `maxEnterPerRound` | 1 | 单窗口硬约束 |

---

## 9. 失败分支

| 情况 | 处理 |
|---|---|
| 列表 OCR 失败 | 不更新 `lastUnread`，下轮重试 |
| 进群后标题认错 | 用点击的行的名称做基准，不一致则以行为准 |
| 找不到「有人@我」标签 | 向上翻 ≤3 屏；仍找不到则只读最新屏并记日志 |
| 滚动 5 秒没停 | 放弃本次，`cooldownUntil = now + 90s` |
| 中途被电话/通知打断 | 回 A，未读数不更新 |
| 发送失败（风控/网络） | 关串，回 A，记 `sendFail` |
| 4B 超时（>10s） | 本帧跳过，不回退到 rapidocr（避免卡顿雪崩） |

| 现有 | 改造 |

**不动的部分**：发送链路（`wechat_send`）、风控守卫、`wechat_inbox`、唤醒提示词。

## 11. 分阶段落地

| 阶段 | 内容 | 风险 | 可回滚 |
|---|---|---|---|
| **P0** | 修「浮层/引用行」噪声：OCR 结果里过滤 `微信：` `引用：` 等横幅行；标题裁剪避开横幅区 | 低 | 是 |
| **P1** | 讨论串优先：串活着时不扫列表（其实现在也没扫，先加状态位） | 低 | 是 |
| **P2** | 列表扫描 + 进群（只做"未读数↑ → 进群 → 读最新屏"） | 中 | 是 |
| **P3** | 「有人@我」标签跳转 + 等滚动停 | 中高 | 是 |
| **P4** | 多群选择策略（优先级、配额、黑白名单） | 中 | 是 |

每阶段都可单独上线、单独回滚。

## 12. 未验证项（必须实测）

1. 列表行被 @ 后是否显示 `[有人@我]` 且**保留**（决定 P2 能否省掉进群判断）。
2. 「有人@我」标签的确切文案/坐标/是否只在有未读 @ 时出现。
3. 点击标签后滚动动画的实际时长（不同消息量下的分布）。
4. 4B 对"列表页"的 OCR 准确率（8~10 行的紧凑列表 vs 聊天区）。
5. 私聊 / 群聊 在列表预览上的识别准确率（昵称前缀规则是否稳）。

## 13. 风险

- **微信 UI 改版**：标签文案、列表布局变化会让 OCR 解析失效 → 用"多特征兜底"，任一特征命中即可。
- **活跃群**：未读数持续增长，可能一直进群 → 靠冷却 + 单轮只进一个抑制。
- **算力**：4B 单帧 2.1s，多群扫描会放大总耗时 → 列表扫描用轻量 OCR（Windows OCR/小模型）先筛，命中才上 4B。
- **单窗口打断**：进群会把正在进行的讨论串切走 → 由 P1 的"串优先"规则禁止。

## 14. 实现现状（2026-11-14，与本文设计的差异）

落地过程中改了几处设计，记在这里免得对不上：

1. **单/多会话是开关不是替换**：`multi.enabled=false` 回到 v0.3.1 的单窗口行为
   （见 [`single-window-design.md`](single-window-design.md)）。本文只描述 `multi.enabled=true`。
2. **私聊也开串**（原设计只给群聊开）：进私聊立刻 `openThread(trigger="dm")`，
   进出窗口统一用"串活着就留着、串散了就回列表"；私聊串闲置 `dmThreadTtlMin`（5 分），
   群串 `threadTtlMin`（10 分）。
3. **串续命只认"对着她说的"**：@ / 引用回复她 / 她自己说话。
   原设计是"串里有新消息就续"，实测热闹的群能把串续到 50 分钟。
4. **@ 去重用指纹**（会话 + 那句前 12 字，15 分钟）：本地 VL 对同一行措辞会抖，
   靠原文去重会失效，一条 @ 被当成新的反复唤醒。
5. **发送前核对**：`wechat_send` 带 `chat` 参数，标题对不上就拒发（原设计没有这一层，
   实测把群里的回头发进了私聊）。
6. **群里主动开口默认关**（`proactiveInGroups`）：进来只为看一眼的群，不该自己说话。
7. **列表识别用 Windows OCR + 像素红点**：红点 OCR 读不出（红底白字），改数头像右上角红色像素。
8. **顶部"微信"自检用 scale=3**：细体两字在 scale=2 下读不出，会让轮询误判"不在列表"。
